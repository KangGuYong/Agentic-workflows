# Agentic Workflow Builder MVP — Plan Roadmap

Spec: `docs/superpowers/specs/2026-09-11-agentic-workflow-builder-mvp-design.md`

The MVP spec covers three independently testable subsystems. Each gets its own plan, written only after the previous one lands, so later plans are written against real interfaces instead of guesses.

| Plan | Scope | Status | Depends on |
|---|---|---|---|
| 1. Engine core | DSL, types, templates, nodes (8 of 9), validator, compiler, in-process runner, Ollama transport | **Written:** `2026-09-11-engine-core.md` | — |
| 2. Runtime service | Postgres/Redis/FastAPI/worker: run state machine, leases, events/SSE, API, HITL/retry/cancel, `http_request` node, secrets, redaction, retention | To write after Plan 1 | Plan 1 |
| 3. Web editor | Next.js + React Flow canvas, schema-driven forms, validation display, test runs, trace panel, approval UI | To write after Plan 2's API is stable | Plan 2 |

## Plan 2 scope checklist (from spec)

- Postgres schema + Alembic (3.3), `AsyncPostgresSaver` with `EncryptedSerializer` (10.3), `durability="sync"`
- Run state machine, CAS claim, lease/heartbeat/fencing, reaper (5.1, 5.2)
- Postgres `Recorder` with transactional `event_seq`; Redis publish after commit (7.2)
  - One recorder per run.
  - `node_started` maps the unique-key conflict to `DuplicateAttempt`.
  - Closing an attempt works on a row that is already closed, because a replay reuses the waited attempt and can emit `node_finished` twice.
  - `node_token` is best effort.
  - Close orphaned `running` rows at run level on cancel or recovery.
- Worker fault handling: when the run task raises `EngineFault`, `LeaseLost` or any unexpected exception, stop the heartbeat or do a fenced requeue (`recovery_count + 1`). A live heartbeat would keep the run `running` forever.
- SSE endpoint: subscribe → replay → dedupe → gap fill; token events without `id:` (7.3)
- API contract, error codes, optimistic locking, version-confirm transaction, `Idempotency-Key` (8)
- Resume/retry/cancel flows incl. `resume_payload`, `RESUME_TARGET_MISMATCH`, `RUN_DATA_EXPIRED` (5.5, 5.6, 5.9)
  - Check the resume body with `engine.nodes.human_approval.resume_output(body, waiting)`. `waiting` is the stored interrupt payload. Do this before `waiting → queued`, so a bad answer gets a 422 and does not fail the run after resume.
  - Pass the answer to `execute_run(resume=…)` with `nodeId`/`execIndex`, and store them in `resume_payload`. Clear `resume_payload` whenever the resumed invocation returns, whatever the outcome; a leftover payload on a failed run acts like a retry. On `ResumeRejected`, keep the run `waiting`. Keep `409 RESUME_TARGET_MISMATCH` in the API: the engine silently continues when the named approval is not the one waiting (that is how a replayed answer is ignored).
  - Set `reviewedAt` to the server time when the answer is accepted. Never copy it from the request: `resume_output` accepts any valid timestamp it is given, so the API must strip or overwrite `reviewedAt` before calling it and before saving `resume_payload`.
- `http_request` node: egress policy, DNS pinning, redirect re-checks, size caps, idempotency key `run:node:exec_index`, POST/PATCH default attempts (4.7, 5.4, 10.5)
- Secrets store (AES-GCM, write-only API, `{{secret.X}}` only in `http_request`), redaction (10.2, 10.3)
- `storeRunData`, retention purge, log policy (10.1, 10.4)
- Limits: DSL size 512KB, inputs 256KB, run active time 1h, waiting 30 days (11.1)
- Redis per-model LLM semaphore with TTL (6.4)
- Template render deadline: engine rules keep every value a template builds linear in (template length + data size), but CPU is not bounded — one loop whose body scans the data (e.g. `{% for x in d %}{{ d | tojson | length }}{% endfor %}`) costs O(data size²) with almost no output, so an output cap never triggers (measured: 20k-item list, 2k iterations ≈ 7.7 s). Synchronous rendering cannot be interrupted by `asyncio.timeout`. Run node rendering off the event loop in a process pool with a hard deadline and memory limit in the worker container.
- Failed-attempt token usage: `LLMGateway` sums tokens across repair calls but a final `STRUCTURED_OUTPUT_FAILED` (and any NodeError after an LLM call) carries no usage, and Plan 1's recorder records usage only on success. Carry usage on `NodeError` (or report it through the recorder per attempt) so cost/metrics include failed attempts.
- Synchronous CPU work on the event loop. Template rendering and `engine.jsondata.schema_violations` run synchronously; validation is capped at about 3 s by its step budget, and rendering is not capped. Run node execution's CPU-heavy parts off the loop, in a thread or process with a deadline, so one tenant cannot stall other runs. Also re-weight validation steps by keyword. Wide unions spend the budget fastest: data matching late in a 16-branch `anyOf` exhausts it at about 0.4 MB.
- Strict JSON at the API boundary. Parse DSL bodies and run inputs with `engine.jsondata.parse_json`, since FastAPI/`json.loads` accept NaN and duplicate keys. Reject or strip NUL in node text outputs, such as raw model text, before storing them in Postgres `jsonb`, which rejects `\u0000`.
- Validation CPU per request: the shared step budget still lets one save or run request force about 2 s of schema validation, and template parsing within the 512 KB DSL limit about 3–4 s more. Run `validate()` off the event loop and rate-limit saves per workspace.
- Strict DSL coercion: `Policy`/`RetrySpec` accept `timeoutSec: true` (→ 1) and `"3"` (→ 3). Use pydantic strict mode for DSL models at the API boundary.
- Checkpoint growth: every node output lives in the one `outputs` channel, and LangGraph saves a new copy of a changed channel at every step, so checkpoint storage grows quadratically with run length. Measured: 40 template nodes carrying a 250 KB input wrote 226 MB for one run. Before Postgres checkpoints go live, either give each node its own output channel (a state type built per workflow, with `outputs` assembled for rendering) or cap total run state in the wrapper, and prune old checkpoints of finished runs.
- One node registry: `analyze`, `validate` and `compile_workflow` each build `default_registry()` when `registry=` is omitted. Once `http_request` is registered, a call that forgets `registry=` judges the same DSL differently. Build one configured registry per process and pass it everywhere, or make the parameter required.
- Version dedupe: `dsl_hash` hashes `policy: {}` and a missing policy differently, though both mean "no override". Normalize empty policies before hashing.
- Run state depth: values kept in run state are limited to `engine.jsondata.MAX_JSON_DEPTH` (100) nesting levels, because LangGraph's checkpoint serializer fails at about 250. Parse run inputs with the same limit at the API (422), rather than relying on the runner's failed outcome.
- Concurrency check: add a characterization test that concurrent `ainvoke`s on one cached compiled graph keep their `Runtime` contexts separate (worker runs many runs per process).
- Docker Compose: web, api, worker, postgres, redis, ollama

## Plan 3 scope checklist (from spec 9)

- Palette from `/node-types`, immutable `<type>_<n>` ids, labels, ELKjs auto-layout, undo/redo
- RJSF settings tab + policy tab, template inputs with `{{` autocomplete and label chips
- Template help text for non-developers (engine rules from Plan 1): join values by writing `{{ a }}{{ b }}` side by side (`~` and string `+` are rejected); arithmetic is numbers-only; loops cannot nest; nesting depth ≤ 50; a rendered field is at most 1,000,000 chars; `default(x)` replaces only a missing value, not `null` (suggest `default(x, true)` when null should count as missing). JSON-format template nodes: each `{{ }}` inserts a JSON value, so write `{"name": {{ start.name }}}` without quotes and without `| tojson` (tojson would double-encode). Build strings inside a text template node first. Values (inputs, node outputs, edited approval values, default outputs) can nest at most 100 levels.
- Schema editor for start inputs and LLM `outputSchema`: offer only the engine's tenant subset (the keywords `engine.jsondata.schema_problems` accepts: type, properties, required, additionalProperties, items, anyOf/oneOf, enum/const, numeric and length/count bounds ≤ 10,000, annotations). Show `schema_problems` messages inline.
- Loops and merges (engine rules from Plan 1 Task 13):
  - An edge that closes a cycle from a condition or classifier asks for `maxIterations`, which marks it as the back-edge.
  - A condition self-loop gets a warning.
  - The merge node's help text says the merged output holds every branch and can hit the 1 MB output cap.
- Validation badges (error/warning), run button disabled on errors
  - Config and policy issues embed pydantic's English `msg` after a Korean prefix. Map them to Korean by pydantic error `type` (API or editor).
  - A workflow over the node or edge limit returns only `LIMIT_EXCEEDED`, with no per-node issues. Show it as a banner.
- Autosave with `revision`, 409 conflict dialog
- Test run with `Idempotency-Key`, live node states over SSE (`Last-Event-ID` reconnect), token preview
- Trace panel by exec_index/attempt, approval dialog, cancel ("취소 중")
- Playwright E2E per spec 12
